# Issue Tree

## 1. Name

Issue Tree

## 2. Category

Strategy / Problem Structuring

## 3. Purpose

Break a complex business problem into smaller, logically distinct questions that can be analyzed independently.

The Issue Tree is primarily a problem-structuring tool. It helps transform a broad business question into a set of specific questions that can be investigated with evidence and analysis.

It should help LOHITH OS determine:

- What exactly needs to be understood?
- What are the major drivers of the problem?
- Which questions need to be answered?
- Which branches require data?
- Which branches can be eliminated or deprioritized?
- Which analytical frameworks should be applied to each branch?

## 4. Core Question

"What are the major components or drivers of this problem, and what questions must be answered to solve it?"

## 5. Use When

Use an Issue Tree when:

- The business problem is broad or ambiguous.
- Multiple possible causes exist.
- The problem has several drivers.
- The analysis requires investigation across multiple dimensions.
- The team needs to structure an unfamiliar problem.
- The root cause is not yet known.
- Multiple hypotheses need to be tested.
- The problem crosses functions or business units.
- The decision requires several independent analyses.

Typical examples:

- Revenue is declining.
- Profitability has deteriorated.
- Customer churn increased.
- Growth has slowed.
- A company is considering entering a new market.
- A company wants to automate a process.
- A product is underperforming.
- An organization wants to reduce operating costs.

## 6. Do NOT Use When

Do not use an Issue Tree as the primary analytical tool when:

- The problem is already narrowly defined.
- The required calculation is straightforward.
- The answer is already known and only execution remains.
- A specialized analytical method directly answers the question.
- The issue tree would create unnecessary complexity.

Examples:

If the question is:

"How much revenue did we generate last month?"

An Issue Tree is unnecessary.

If the question is:

"Why did revenue decline 20%?"

An Issue Tree is highly useful.

## 9. Key Questions

Before constructing the tree:

1. What is the exact problem?
2. What decision must ultimately be made?
3. What outcome is currently different from expectations?
4. What are the major possible drivers?
5. Can the drivers be separated logically?
6. Are the branches mutually exclusive where appropriate?
7. Are the branches collectively sufficient to answer the question?
8. Which branches can be measured?
9. Which branches require qualitative investigation?
10. Which branches are most likely to contain the root cause?
11. Which branches have the greatest potential impact?
12. Which branches can be eliminated quickly?

## 11. Analysis Process

### Step 1 — Define the top-level question

Express the problem as a question.

Weak:

"Revenue problem."

Better:

"Why has revenue declined by 20% over the last six months?"

Best:

"What are the primary drivers of the 20% revenue decline, and which interventions can restore revenue to the target level?"

### Step 2 — Identify major branches

Break the problem into major drivers.

For example:

Revenue decline:

Revenue
├── Customer volume
└── Revenue per customer

Customer volume can then be decomposed into:

Customer volume
├── New customers
└── Existing customers

Existing customers can then be examined through:

Existing customers
├── Retention
└── Reactivation

Revenue per customer can be decomposed into:

Revenue per customer
├── Price
├── Purchase frequency
└── Product / service mix

### Step 3 — Continue decomposition

Continue breaking branches down until each branch becomes:

- measurable,
- testable,
- actionable,
- or sufficiently specific for another framework.

Do not decompose simply for the sake of creating more branches.

### Step 4 — Test logical completeness

Ask:

"Would investigating these branches be sufficient to answer the original question?"

If not, identify missing branches.

### Step 5 — Test overlap

Ask:

"Are two branches measuring the same underlying factor?"

If yes, restructure the tree.

### Step 6 — Prioritize branches

Prioritize using factors such as:

- Expected impact
- Probability
- Evidence availability
- Cost of investigation
- Strategic importance
- Urgency

### Step 7 — Assign analytical methods

Each branch may require a different framework.

Example:

Revenue decline

├── Customer decline
│   ├── Acquisition → Funnel Analysis
│   └── Retention → Cohort Analysis
│
└── Revenue per customer decline
    ├── Price → Price Analysis
    ├── Frequency → Customer Behavior Analysis
    └── Mix → Product Mix Analysis

The Issue Tree therefore becomes a bridge between:

Problem Definition

→ Questions

→ Hypotheses

→ Evidence

→ Frameworks

→ Analysis

## 12. Expected Output

The output should contain:

1. Clearly defined top-level problem.
2. Decision or objective.
3. Major branches.
4. Sub-branches where necessary.
5. Hypotheses associated with important branches.
6. Evidence required for each branch.
7. Recommended analytical framework for each branch.
8. Priority of investigation.
9. Open questions.
10. Branches that can be eliminated.

## 13. Interpretation

An Issue Tree does not itself provide the answer.

It provides the structure required to find the answer.

LOHITH OS should therefore treat an Issue Tree as an investigation map.

The existence of a branch does NOT mean that the branch is a confirmed cause.

For example:

Revenue decline
└── Customer retention

does not mean:

"Customer retention caused the revenue decline."

It means:

"Customer retention is a hypothesis that should be investigated."

This distinction is critical.

## 14. Limitations

Issue Trees can fail when:

- The top-level problem is poorly defined.
- Branches are based on assumptions rather than evidence.
- The tree becomes excessively detailed.
- Branches overlap.
- Important drivers are omitted.
- The structure is forced into a predetermined framework.
- The team confuses hypotheses with facts.
- The tree is treated as the analysis rather than a structure for analysis.

An Issue Tree should remain flexible as evidence changes.

## 15. Common Mistakes

### Mistake 1 — Starting with frameworks

Bad reasoning:

"We need to use SWOT."

Better reasoning:

"We need to understand the problem first. What questions must be answered?"

### Mistake 2 — Treating assumptions as facts

Bad:

"Customers are leaving because prices increased."

Better:

"Price increases may be contributing to churn. Test this hypothesis."

### Mistake 3 — Over-decomposition

Creating dozens of branches does not automatically create better analysis.

Decompose only when the additional level improves understanding or enables a meaningful investigation.

### Mistake 4 — Mixing levels

Example:

Revenue
├── Marketing
├── Customers
└── Pricing

These are not necessarily at the same analytical level.

A better structure might be:

Revenue
├── Number of customers
└── Revenue per customer

Then investigate marketing as a driver of customer acquisition.

### Mistake 5 — Ignoring the decision

The tree should ultimately help answer a business decision.

A perfectly structured tree that does not inform a decision has limited value.

## 18. Decision Impact

High.

Issue Trees can determine the entire direction of an analysis.

A poor issue structure can cause the organization to investigate the wrong problem.

A strong issue structure allows LOHITH OS to:

- identify the most important questions,
- eliminate irrelevant analysis,
- allocate analytical effort,
- identify missing evidence,
- connect problems to frameworks,
- and ultimately improve decision quality.

## 19. Consulting Judgment

LOHITH OS should not automatically generate an Issue Tree for every problem.

It should first determine whether the problem is sufficiently broad or ambiguous to justify one.

When creating an Issue Tree, LOHITH OS should:

1. Start from the decision.
2. Define the outcome that must be explained or changed.
3. Identify the major drivers.
4. Prefer causal or economic relationships where possible.
5. Avoid arbitrary categories.
6. Separate facts from hypotheses.
7. Ensure branches are logically coherent.
8. Avoid unnecessary depth.
9. Prioritize branches using impact and evidence.
10. Connect branches to specific analytical methods.
11. Update the tree when evidence invalidates a branch.

The tree is a living reasoning structure, not a static diagram.

## 20. Framework Reasoning Rule

Use an Issue Tree when the primary challenge is:

"We do not yet know how to structure this problem."

Do not use it merely because it is a common consulting framework.

The correct sequence is:

Problem
→ Decision
→ Question
→ Structure
→ Hypotheses
→ Evidence
→ Analysis

not:

Problem
→ Framework
→ Answer

## 21. Framework Chain

Typical chain:

Problem Definition

→ Synthesis
→ Recommendation

## 22. Framework Combination Rules

### Issue Tree + MECE

Use MECE principles to test whether the branches are sufficiently distinct and collectively comprehensive.

### Issue Tree + Hypothesis Tree

Use an Issue Tree to structure the problem and a Hypothesis Tree to organize potential explanations.

### Issue Tree + Root Cause Analysis

Use Root Cause Analysis when a branch appears to contain a meaningful underlying cause that requires deeper investigation.

### Issue Tree + Specialized Framework

Assign specialized frameworks to individual branches rather than forcing one framework across the entire problem.

### Issue Tree + Quantitative Analysis

Use quantitative analysis to validate or eliminate branches.

## 23. Framework Selection Hierarchy

When deciding whether to use an Issue Tree:

1. Is the problem broad?
2. Is the decision unclear?
3. Are multiple explanations possible?
4. Are multiple analytical questions required?
5. Does decomposition make the problem easier to investigate?

If most answers are yes, use an Issue Tree.

## 24. Quality Standard

A high-quality Issue Tree should:

- Start with a precise problem.
- Connect directly to a decision.
- Have logically meaningful branches.
- Avoid unnecessary overlap.
- Distinguish hypotheses from facts.
- Identify evidence requirements.
- Enable prioritization.
- Connect branches to appropriate analytical methods.
- Remain adaptable as new evidence appears.
- Lead toward an actionable recommendation.

The ultimate test is:

"Does this structure make it easier to determine what the business should do next?"
