# LOHITH OS — FRAMEWORK KNOWLEDGE SCHEMA

## Purpose

Every consulting framework in LOHITH OS should be represented as a reasoning tool rather than merely a framework name.

A framework definition should help the AI answer:

1. What is this framework?
2. What problem does it solve?
3. What question does it answer?
4. When should it be used?
5. When should it NOT be used?
6. What evidence does it require?
7. How should it be applied?
8. What does its output mean?
9. What are its limitations?
10. What frameworks should come before it?
11. What frameworks should come after it?
12. What frameworks can be combined with it?
13. What mistakes should the consultant avoid?

---

# Framework Definition

Every framework should contain the following sections.

## 1. Name

The official name of the framework.

## 2. Category

Examples:

- Strategy
- Growth
- Finance
- Marketing
- Customer
- Operations
- Product
- Organization
- Technology
- AI
- Implementation

## 3. Purpose

Explain what the framework is designed to accomplish.

The purpose should describe the analytical job performed by the framework.

## 4. Core Question

The primary business question the framework answers.

Example:

> "How attractive is this industry structurally?"

## 5. Use When

Conditions under which the framework is useful.

## 6. Do NOT Use When

Situations where the framework is inappropriate, insufficient, or likely to create misleading conclusions.

This section is critical.

A strong consultant should know when NOT to use a framework.

## 7. Problem Types

The types of business problems for which the framework is relevant.

Examples:

- Strategy
- Market Entry
- Growth
- Profitability
- Customer
- Operations

## 8. Decision Types

The type of decision supported by the framework.

Examples:

- Diagnose
- Decide
- Optimize
- Predict
- Prioritize
- Design
- Implement

## 9. Key Questions

List the questions that should be answered while applying the framework.

## 10. Required Inputs

Specify the evidence/data required.

Examples:

- Market size
- Competitor information
- Customer data
- Financial data
- Operational data

## 11. Analysis Process

Explain how a consultant should actually use the framework.

This should be procedural.

## 12. Expected Output

Describe what the framework should produce.

Examples:

- Industry attractiveness assessment
- Root-cause tree
- Strategic options
- Financial scenarios
- Prioritized initiatives

## 13. Interpretation

Explain how the output should be interpreted.

The framework should never be treated as producing a recommendation automatically.

## 14. Limitations

Explain what the framework cannot tell us.

## 15. Common Mistakes

Identify common analytical mistakes.

Examples:

- Treating assumptions as facts.
- Using outdated information.
- Double counting factors.
- Confusing correlation with causation.
- Using the framework without sufficient evidence.

## 16. Compatible Frameworks

Frameworks that can logically be combined with this framework.

## 17. Framework Sequence

Specify frameworks that commonly come:

### Before

What analysis should happen first?

### After

What analysis should happen next?

## 18. Decision Impact

Explain how the framework can change the final business decision.

## 19. Consulting Judgment

This is the most important section.

Explain what an experienced consultant should notice that a mechanical framework application might miss.

# Framework Reasoning Rule

LOHITH OS must never reason:

> "This problem is about strategy, therefore use SWOT."

Instead:

> "What decision must be made?"

Then:

> "What must we understand to make that decision?"

Then:

> "What analytical question does each framework answer?"

Then:

> "What evidence is required?"

Then:

> "Which framework should be applied first?"

Then:

> "What should the result of that analysis cause us to investigate next?"

---

# Framework Chain

Frameworks should be treated as nodes in a reasoning chain.

```text
Business Problem
      ↓
Business Question
      ↓
Evidence Required
      ↓
Framework
      ↓
Finding
      ↓
Insight
      ↓
Next Question
      ↓
Next Framework
```

A framework is therefore not the answer.

A framework is a tool for producing evidence that helps answer a business question.

---

# Framework Combination Rules

LOHITH OS may combine frameworks when:

1. One framework answers only part of the problem.
2. The frameworks examine different dimensions.
3. The output of one framework becomes an input to another.
4. Combining them reduces uncertainty.
5. They provide complementary rather than duplicate analysis.

LOHITH OS should avoid combining frameworks when:

1. They answer the same question.
2. They create duplicate analysis.
3. One framework already provides sufficient evidence.
4. The combination adds complexity without improving the decision.

---

# Framework Selection Hierarchy

Use this order:

```text
1. Business Decision
        ↓
2. Business Question
        ↓
3. Problem Type
        ↓
4. Analytical Question
        ↓
5. Evidence Required
        ↓
6. Framework Selection
        ↓
7. Framework Sequence
        ↓
8. Analysis
        ↓
9. Synthesis
        ↓
10. Recommendation
```

---

# Quality Standard

A framework recommendation is not considered high quality unless LOHITH OS can explain:

- Why the framework was selected.
- What question it answers.
- What evidence it requires.
- What it will produce.
- What it cannot tell us.
- What should happen after the analysis.
